> 말만 하던 LLM에게 계산기·검색·로봇 팔 같은 '손발'을 달아주는 장치 — 필요할 때 정해진 형식으로 도구를 불러 쓰게 한다.

**대표 논문**: Toolformer: Language Models Can Teach Themselves to Use Tools (2023) / OpenAI Function Calling (2023) · **분류**: 아키텍처 모듈

## 해결한 문제
LLM은 학습할 때 외운 지식에 갇혀 있어서 최신 정보나 정확한 계산, 실시간 데이터에는 약하다. '계산해서 알려줘'라고 하면 그럴듯하지만 틀린 숫자를 자신 있게 말하기 일쑤다. 또 외부 시스템과 연결하려면 모델 출력에서 JSON을 억지로 뽑아내는 접착 코드를 매번 새로 짜야 했다.

## 핵심 아이디어
비유하면 똑똑한 비서에게 전화번호부와 계산기를 쥐어주는 것 — 말로 답을 지어내는 대신 필요하면 직접 눌러보게 한다. 작동 순서는 이렇다. ① 개발자가 '쓸 수 있는 도구 목록'(이름, 설명, 어떤 인자를 받는지)을 모델에게 미리 보여준다. ② 모델이 필요하다고 판단하면 자연어 대신 정해진 JSON 형식으로 '이 함수를 이 인자로 불러달라'고 출력한다. ③ 실제 실행은 모델이 아니라 바깥 프로그램(호스트)이 대신 한다. ④ 실행 결과를 다시 대화에 넣어주면 모델이 그걸 읽고 최종 답을 만든다.

## 왜 작동하나
모델은 확률로 그럴듯한 텍스트를 만들 뿐이라 정확한 계산이나 최신 정보를 보장하지 못한다. 도구 호출은 그 부분을 결정론적 프로그램이나 실시간 API에 넘겨버리므로 정확성과 최신성이 확보된다. 또 출력이 구조화된 JSON이라 파싱이 쉽고, 어떤 도구를 쓸지 모델이 스스로 고르기 때문에 개발자가 모든 분기를 일일이 짜지 않아도 된다.

## 트레이드오프
- 도구 설명이 길어질수록 컨텍스트를 잡아먹고 비용과 응답 지연이 늘어난다.
- 모델이 엉뚱한 도구를 고르거나 인자를 잘못 채우는 오류(환각)가 여전히 남는다.
- 여러 단계 호출이 이어지면 느려지고, 중간에 잘못된 결과가 나오면 뒤 단계까지 연쇄로 틀어질 수 있다.
- 모델이 임의의 외부 API를 부를 수 있으므로 권한 제한과 검증 계층을 따로 두어야 안전하다.

## 계보
**이전**
- ReAct (추론+행동을 번갈아 하는 프롬프트 기법)
- 프롬프트로 JSON 출력 형식을 강제하던 수작업 파싱
- 검색 증강 생성(RAG)

**이후**
- MCP (Model Context Protocol, 도구 연결 표준)
- [[techniques/tool-calling|병렬 Tool Calling / 멀티툴 에이전트 프레임워크]]
- Code-as-Action (도구 대신 코드를 써서 행동하는 방식)

## 피지컬 AI에서의 쓰임
- VLA(로봇 파운데이션 모델)에서 '컵 집어줘' 같은 고수준 명령을 '이동→그리퍼 닫기→들어올리기' 같은 로봇 API 호출로 바꿔 실행한다.
- 월드모델·시뮬레이터에서 물리 엔진 쿼리나 시뮬레이션 스텝 실행을 도구로 불러 계획을 검증한다.
- LLM 에이전트가 검색·계산·DB 조회 도구를 불러 최신 정보로 답하거나, 로봇 상태 조회 API를 호출해 상황을 확인한다.

## 💡 아이디어 훅
- 로봇 도구의 '설명문'을 어떻게 쓰느냐가 모델의 도구 선택 정확도를 얼마나 바꿀까? 설명 자체를 학습시키면?
- 도구 호출이 실패했을 때 스스로 알아채고 다른 인자로 재시도하는 루프를 어떻게 설계할까?
- 성공한 도구 호출 로그를 모아 정책을 파인튜닝하면, 적은 데이터로도 도구 선택 능력을 키울 수 있지 않을까?
