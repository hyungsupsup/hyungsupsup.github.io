> 그림 그리는 일을 CPU가 GPU에 부탁하지 않고 GPU 안에서 처음부터 끝까지 처리해서, 수천 개 로봇 환경의 카메라 영상을 한꺼번에 뽑아내는 방식

**대표 논문**: Isaac Gym: High Performance GPU-Based Physics Simulation For Robot Learning (2021) — GPU 네이티브 렌더링/시뮬레이션 흐름의 대표 사례 · **분류**: 로봇 특화

## 해결한 문제
예전 시뮬레이터는 물리 계산은 CPU에서 하고 '이 장면 좀 그려줘'라고 GPU에 매 프레임 부탁하는 구조였다. 그래서 장면 하나 렌더링할 때마다 CPU와 GPU가 서로 기다리는 왕복이 생겼고, 환경을 수천 개 동시에 돌리는 강화학습에는 속도가 너무 느렸다. 게다가 렌더링 결과 이미지가 GPU 밖으로 복사돼야 해서, 그 이미지를 바로 정책 신경망 입력으로 쓰기도 번거로웠다.

## 핵심 아이디어
비유하면 '재료 손질은 주방 밖에서, 조리는 주방 안에서' 하던 걸, 손질부터 플레이팅까지 전부 주방(GPU) 안에서 끝내는 것이다. 작동 순서는 이렇다. (1) 로봇 자세·물체 위치·카메라 파라미터를 전부 GPU 메모리 위의 텐서로 유지하고, (2) 렌더링도 GPU 커널(래스터화나 레이 트레이싱)로 직접 수행해 결과 이미지가 GPU 텐서로 바로 나오며, (3) 그 텐서를 CPU로 복사하지 않고 그대로 정책 네트워크의 입력으로 넘기고, (4) 수천 개 환경을 하나의 배치로 묶어 한 번의 GPU 호출에서 동시에 렌더링한다.

## 왜 작동하나
가장 큰 병목이던 CPU↔GPU 동기화(서로 끝나기를 기다리는 대기)가 사라져 프레임 지연이 크게 줄어든다. 또 환경 수천 개를 배치로 처리하니 GPU 연산 유닛을 거의 꽉 채워 쓸 수 있어, 환경 수를 늘려도 전체 시간이 선형으로 늘지 않는다. 데이터가 이미 GPU에 있으니 렌더링→학습으로 이어지는 파이프라인이 끊김 없이 돌아간다.

## 트레이드오프
- GPU 메모리를 많이 잡아먹어서, 환경 수나 해상도를 올리면 금방 메모리 한계에 부딪힌다.
- 실사급 오프라인 렌더러보다 시각적 사실성이 떨어질 수 있어, sim-to-real(시뮬레이션에서 배운 걸 실기로 옮기는 것) 격차가 커질 위험이 있다.
- GPU가 없는 환경에서는 아예 돌릴 수 없고, GPU 커널 안에서 벌어지는 일이라 디버깅과 오류 추적이 까다롭다.

## 계보
**이전**
- CPU 기반 물리 + OpenGL 클라이언트-서버 시뮬레이터 (MuJoCo CPU, Gazebo 등)
- 프레임 단위로 CPU-GPU를 왕복하던 전통적 그래픽스 파이프라인

**이후**
- Isaac Lab
- MuJoCo MJX (GPU/가속기 네이티브 물리+렌더링)
- Genesis
- 미분 가능 렌더링 계열 (NVDiffRast, NVIDIA Warp 기반 렌더러)

## 피지컬 AI에서의 쓰임
- 수천 개 로봇 환경을 병렬로 돌려 카메라 이미지 기반 정책을 대규모 강화학습으로 학습시킬 때 쓴다.
- 조명·질감·카메라 위치를 무작위로 바꾸는 domain randomization(도메인 무작위화)으로 시뮬레이션 카메라 영상을 대량 생성해 sim-to-real 격차를 줄인다.
- VLA(비전-언어-행동 모델)나 월드모델 학습용 합성 관측 데이터를 GPU에서 실시간으로 뽑아낼 때 활용된다.

## 💡 아이디어 훅
- 렌더링을 미분 가능하게 만들면, '원하는 이미지'에서 거꾸로 물체 자세나 조명을 역추정하는 문제에 쓸 수 있지 않을까?
- 실기 로봇의 카메라 스트림도 GPU에서 바로 처리해, 시뮬레이션과 실기를 같은 GPU 파이프라인으로 묶는 '하이브리드 루프'가 가능할까?
- 월드모델이 예측한 미래 장면을 GPU 네이티브로 즉시 렌더링해 정책 학습에 되먹임하면 어떤 이점이 생길까?
