> 여러 에이전트 '변이체'를 만들어 실제 과제로 채점하고, 잘한 놈만 남겨 다음 세대를 만드는 다윈식 에이전트 개선법

**대표 논문**: EvoAgent: Towards Automatic Multi-Agent Generation via Evolutionary Algorithms (2024) — 계열 기법의 대표 예시 (정확한 원조 논문은 확인 필요) · **분류**: 학습 기법

## 해결한 문제
지금까지 에이전트(LLM이 도구를 쓰며 과제를 푸는 시스템)는 사람이 프롬프트·역할·도구 조합을 손으로 짜야 했고, 한 번 정하면 성능이 어디서 새는지 알기 어려웠다. 프롬프트를 조금 바꿔보고 싶어도 '어떤 조합이 더 나은지'를 체계적으로 비교할 방법이 없어 감으로 튜닝하는 경우가 많았다.

## 핵심 아이디어
자연선택처럼, 에이전트를 '한 마리'가 아니라 '한 무리'로 키운다. (1) 여러 변이체를 만든다 — 프롬프트 문구, 역할 분담, 사용하는 도구, 추론 순서 등을 조금씩 바꾼 사본들. (2) 각 변이체를 실제 과제(질문·태스크)에 투입해 점수(적합도)를 매긴다. (3) 점수 높은 것들을 부모로 삼아 다시 변이·교차시켜 다음 세대를 만든다. (4) 이 과정을 여러 세대 반복하면, 사람이 미처 상상 못한 조합이 살아남는다.

## 왜 작동하나
사람이 한 번에 하나씩 고치는 대신 수십 개 방향을 동시에 탐색하기 때문에, 국소적으로만 좋아 보이는 함정에서 벗어나기 쉽다. 또 '실제 과제 점수'라는 객관적 신호로 걸러내므로, 그럴듯해 보이지만 실제로는 성능이 떨어지는 변이는 자동으로 도태된다. 변이를 LLM 스스로 생성하게 하면 사람이 손으로 짜는 것보다 훨씬 넓은 설계 공간을 뒤질 수 있다.

## 트레이드오프
- 변이체마다 실제 과제를 돌려 채점해야 해서, 한 번 진화시키는 데 토큰·시간·비용이 크게 든다.
- 적합도(점수) 함수를 잘못 설계하면 엉뚱한 방향으로 진화한다 — 예를 들어 '짧은 답'만 높게 채점하면 성실한 에이전트가 도태된다.
- 세대를 거듭해도 처음 무리에서 크게 벗어나지 못하는 국소 최적에 갇힐 수 있고, 실행마다 결과가 달라 재현이 어렵다.

## 계보
**이전**
- 수동 프롬프트 엔지니어링
- AutoPrompt / OPRO (프롬프트 자동 최적화)
- 단일 에이전트 프롬프트 튜닝

**이후**
- Darwin Gödel Machine (자기 코드를 스스로 고치는 진화형 에이전트)
- AlphaEvolve 계열 진화형 코드 탐색
- Self-Evolving Agents (자기 진화 에이전트 프레임워크)

## 피지컬 AI에서의 쓰임
- VLA(로봇이 언어 지시를 보고 행동하는 정책)의 프롬프트·서브태스크 분해 방식을 여러 변이체로 만들어, 시뮬레이터 성공률로 채점하고 진화시켜 플래너를 개선.
- 로봇 태스크 플래너(예: '컵 집기 → 옮기기 → 놓기' 순서를 짜는 모듈)의 워크플로우를 변이·선택해, 실제 성공률이 높은 계획 패턴을 자동 발견.
- 월드모델(로봇이 미래를 상상하는 시뮬레이터)과 결합해, 실제 로봇에 배포하기 전 시뮬레이터 안에서 정책 변이체를 대량 평가·선택.

## 💡 아이디어 훅
- 적합도 함수를 '실제 로봇 성공률'로 두면, 시뮬레이터와 실기의 격차(sim-to-real gap)를 진화가 스스로 메꿀 수 있을까?
- 변이 연산자를 사람이 아니라 LLM이 직접 설계하게 하면, 진화 속도와 다양성이 얼마나 달라질까?
- 여러 에이전트를 '개체'가 아니라 '종(種)' 단위로 진화시켜, 역할 분담 자체를 진화시키는 건 어떨까?
